Entendiendo los closures en JavaScript

20 de septiembre, 2026 · 5 min de lectura · JavaScript

Durante mucho tiempo traté los closures como un truco de sintaxis, algo que "simplemente funcionaba". Cambió cuando empecé a pensarlos como una consecuencia natural del scope léxico: una función recuerda el entorno en el que fue creada, no el entorno en el que se ejecuta.

El ejemplo más simple: un contador

Cada vez que crearContador() se ejecuta, se crea un nuevo entorno con su propia variable cuenta. La función interna guarda una referencia a ese entorno, aunque crearContador ya haya terminado de ejecutarse.

function crearContador() {
  let cuenta = 0;
  return function () {
    cuenta += 1;
    return cuenta;
  };
}

const contadorA = crearContador();
const contadorB = crearContador();

contadorA(); // 1
contadorA(); // 2
contadorB(); // 1 — tiene su propio entorno

El error clásico del bucle con var

Este es el ejemplo que más ayuda a que el concepto haga clic. Con var, las tres funciones comparten el mismo entorno, así que todas terminan leyendo el valor final de i.

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// Imprime 3, 3, 3

for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0);
}
// Imprime 0, 1, 2 — let crea un entorno nuevo en cada vuelta

Por qué importa en el día a día

Más allá del examen de entrevista, los closures aparecen todo el tiempo: en manejadores de eventos que necesitan recordar un id, en funciones que devuelven funciones configuradas (fábricas), y en patrones de memoización donde una función interna reutiliza una caché guardada en su entorno externo. Entender el mecanismo evita bugs sutiles y hace que ese código deje de sentirse como magia.
