Arreglos y recursividad: mis apuntes de Estructura de Datos

27 de septiembre, 2026 · 5 min de lectura · Estructura de Datos

Empezamos la Unidad 1 de Estructura de Datos y quiero dejar por escrito lo que se quedó de la primera semana, sobre todo porque hay dos ideas que sonaban obvias en la diapositiva y que solo terminé de entender al ver el código.

Estructura de datos vs. tipo de dato abstracto

La primera distinción que anoté: una estructura de datos es una colección de datos que se caracteriza por su organización y por las operaciones que se definen sobre ella. Un tipo de dato abstracto (TDA), en cambio, es un tipo definido por quien programa, no por el lenguaje. En la práctica, cuando defines una clase Alumno con sus propios atributos y métodos, ya estás creando un TDA.

Estáticas vs. dinámicas

La clasificación que vimos depende de si la estructura puede crecer o no en memoria una vez que el programa ya está corriendo:

  • Estáticas: almacenan una cantidad fija de datos, establecida antes de ejecutar el programa. Ejemplo clásico: los arreglos.
  • Dinámicas: su tamaño se puede incrementar o disminuir según se necesite. Aquí entran pilas, colas, listas y árboles.

Arreglos en Java: son objetos

Algo que no tenía tan claro: en Java los arreglos son objetos, así que se crean con new. Se pueden declarar y crear en un solo paso o por separado:

tipo_dato identificador[] = new tipo_elemento[tamaño];

// o en dos pasos:
tipo_dato identificador[];              // declara la variable arreglo
identificador = new tipo_elemento[tamaño]; // crea el arreglo

Y un detalle que se me había pasado: al crear un arreglo, cada elemento recibe un valor predeterminado por el lenguaje (0 para int, null para String), no queda "vacío" de verdad.

Arreglos de objetos en POO

Donde de verdad conecté esto con lo que ya sabía de programación orientada a objetos fue con los arreglos de objetos: un arreglo puede guardar instancias completas de una clase, no solo tipos primitivos.

// 1. Declarar el arreglo de la clase Alumno
Alumno[] lista = new Alumno[5];

// 2. Crear los objetos
Alumno alumno1 = new Alumno("Juan", 181234);
Alumno alumno2 = new Alumno("Ana", 193234);

// 3. Asignarlos al arreglo
lista[0] = alumno1;
lista[1] = alumno2;

// 4. Acceder a sus métodos
System.out.println(lista[0].getNombre() + " " + lista[0].getMatricula());

Recursividad: no es magia, es dividir el problema

La segunda mitad de la unidad fue recursividad: una técnica en la que un método se llama a sí mismo para resolver un problema dividiéndolo en subproblemas más pequeños, hasta llegar a un caso base que detiene la recursión. El ejemplo de siempre, el factorial, es el que más me ayudó a visualizarlo:

public static int factorial(int n) {
    if (n == 0)
        return 1;              // caso base
    else
        return n * factorial(n - 1);
}

Lo que se ve raro al inicio es que la función "confía" en que la llamada siguiente le va a devolver el resultado correcto, y solo se preocupa por combinarlo con su propio paso. La búsqueda binaria en un arreglo ordenado sigue la misma lógica: en cada llamada se divide el conjunto de datos a la mitad, se compara el elemento central con lo que se busca y, según el resultado, se repite la búsqueda solo en la mitad izquierda o derecha, hasta encontrar el valor o quedarse sin rango donde buscar.

El error que marcaron en clase: confundir recursividad con un ciclo

Esta fue la parte que más se quedó grabada. Vimos un ejemplo de una función verMenu() que se llamaba a sí misma solo para repetir un menú cuando el usuario elegía una opción inválida. Se ve como recursividad porque la función se invoca a sí misma, pero no lo es: no hay un problema que se esté dividiendo en subproblemas más pequeños ni un caso base que reduzca algo. Es, literalmente, un ciclo disfrazado de recursividad, y con cada opción inválida se sigue apilando una llamada nueva sin necesidad.
