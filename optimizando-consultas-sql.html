Optimizando consultas SQL lentas

5 de septiembre, 2026 · 4 min de lectura · Bases de datos

Antes de tocar un índice, reviso tres cosas: qué hace realmente el plan de ejecución, cuántas filas se están escaneando frente a las que se devuelven, y si el problema es la consulta o el modelo de datos.

Leer el plan de ejecución

Un EXPLAIN ANALYZE me dice si el motor está usando un seq scan cuando esperaba un index scan, y por qué. La mayoría de las veces el motivo no es la falta de índice, sino un filtro que no puede usarlo: una función aplicada sobre la columna, una comparación de tipos distintos, o un OR mal indexado.

EXPLAIN ANALYZE
SELECT id, total
FROM pedidos
WHERE fecha_creacion >= '2026-01-01'
  AND estado = 'pagado';

Escaneo vs. filas devueltas

Si una consulta escanea un millón de filas para devolver diez, ahí está la señal. Un índice compuesto sobre (estado, fecha_creacion) suele resolver este caso, pero el orden de las columnas en el índice importa tanto como su existencia.

Cuándo el problema no es la consulta

A veces la consulta está bien escrita y el problema es el modelo: una tabla que mezcla datos históricos con datos activos, o una relación que debería estar desnormalizada para este caso de lectura. Ahí ningún índice va a compensar un diseño que no encaja con el patrón de acceso real.
